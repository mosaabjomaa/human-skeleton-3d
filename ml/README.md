# OSSEO X-ray research baseline

## النسخة المرتبطة حاليًا بعد استيراد Colab

`osseo-fracatlas-yolo11s-colab-v2`، نموذج YOLO11s بدقة 640، وتدريب جميع الطبقات على 2806 صورة. العتبة 0.15 اختيرت على validation. اختبار 603 صور: precision للمواقع 58.4%، recall للمواقع 46.8%، حساسية وجود اقتراح على صور الكسور 64.8%، ونوعية الصور 97.6%. **لم يحقق هدف precision/recall الداخلي 80% وليس معتمدًا طبيًا.** عدم الكشف لا يعني سلامة الصورة.

اختيار الأوزان والتقرير في `artifacts/active-model.json`. الأوزان المستوردة محفوظة مع تقرير Colab الأصلي وبصمتها في `artifacts/colab-import/`؛ النسخة السابقة محفوظة. `import_candidate.py` يتحقق من بصمة الأوزان ومن ثبات تقسيم البيانات ويعيد حساب المقاييس من التنبؤات قبل تحديث manifest. السيرفر يقرأ دقة الإدخال والعتبة من تقرير النسخة المختارة. أعد تشغيل الخدمة بعد تبديل manifest.

أقسام النموذج الخفيف أدناه توثق النسخة السابقة؛ إعداد التدريب الكامل في `train_full.py` وحزمة Colab في `colab/`.

## ما الذي يعمل؟

خيار **مختبر الأشعة / X-ray lab** في أعلى الموقع يرفع صورة JPEG/PNG/WebP إلى خدمة Python محلية. النموذج يستخدم أوزانًا مدرّبة فعليًا على FracAtlas، وليس نتيجة عشوائية أو إجابة نموذج لغوي. المربعات تمثل اقتراحات تجريبية؛ **لا تمثل تشخيصًا**. درجات النموذج ليست احتمالات طبية معايرة.

هذا baseline بحثي محدود، وليس نظامًا جاهزًا لفحص المرضى. عدم ظهور مربع **لا يستبعد الكسر أو الشعر**. لا توجد فئات تدريب للرضّة أو أنواع الكسور، ولا تحقق خارجي أو دراسة سريرية. لا تستخدم النتائج لاتخاذ قرار علاجي.

مصدر حدود الأشعة: [RadiologyInfo، ACR/RSNA](https://www.radiologyinfo.org/en/info/bonerad): بعض الكسور الخفية والرضوض العظمية قد لا تظهر بالأشعة العادية. لذلك لا نعامل النتيجة السلبية كدليل على سلامة العظمة.

ربط المجسم **يدوي**: يختار المستخدم العظمة وجهتها ثم يضيء التطبيق العظمة كاملة. لا ندعي تحويل مربع ثنائي الأبعاد إلى نقطة كسر ثلاثية الأبعاد. ذلك يحتاج تحديد العظام والجهة ومعايرة الصورة واتجاه التصوير والتحقق من التسجيل الهندسي، وغالبًا صورًا متعددة.

## التشغيل على Windows

من مجلد `human-skeleton-3d`:

```powershell
npm run dev -- --port 5174
```

أمر `npm run dev` يشغل Vite وسيرفر Python المحلي معًا، أو يعيد استخدام السيرفر إذا كان شغالًا. السيرفر على `127.0.0.1:8001` وVite يمرر `/api/xray` إليه. لتشغيل الخدمة منفصلة استخدم `npm run ml:serve`. تحتاج بيئة Python الموضحة أدناه. صفحة المختبر تفحص الجاهزية كل عشر ثوانٍ. لا يحتاج التحليل إلى API key أو قاعدة بيانات أو اتصال بالإنترنت بعد تجهيز النموذج.

## إعادة التجهيز والتدريب

Python 3.12، CPU، جميع الملفات داخل هذا المشروع:

```powershell
py -3.12 -m venv ml/.venv
ml/.venv/Scripts/python.exe -m pip install -r ml/requirements.txt --extra-index-url https://download.pytorch.org/whl/cpu
npm run ml:download
npm run ml:train
npm run ml:serve
```

أول تدريب ينزل أوزان YOLO11n من المصدر الرسمي ويخزنها في `ml/cache`. سكربت تنزيل البيانات يثبت FracAtlas v7 ويفحص MD5 المنشور ويرفض مسارات فك ضغط خارج `ml/data`.

## الخوارزمية والملفات

النموذج النشط YOLO11n يبدأ بأوزان COCO ويجمد أول 10 طبقات، ثم يتعلم كشف الكسور على 1000 صورة تدريب: جميع صور الكسور الخمسمائة في train مع 500 صورة سلبية مختارة ببذرة 2026. التحقق والاختبار على المجموعتين الكاملتين بانتشارهما الطبيعي؛ لا تؤخذ صور من test للتدريب. المدخلات 320×320، AdamW، و15 جولة مستهدفة. تُختار checkpoint بالـvalidation.

- `train_yolo.py`: تجهيز مجموعة التدريب المتوازنة وتدريب detector.
- `evaluate_yolo.py`: اختيار العتبة على validation، ثم حساب TP/FP/FN وprecision/recall على test فقط.
- `server.py`: FastAPI، تحميل الأوزان محليًا، معاينة أمثلة من الاختبار، وتحليل الصور في الذاكرة.
- `artifacts/yolo-detector.pt`: الأوزان المستخدمة؛ `yolo-metrics.json`: المقاييس والعتبة والإعدادات وبصمة SHA256 للأوزان؛ `yolo-split.json`: معرفات الصور والتسميات وبصماتها؛ `yolo-predictions.json`: تنبؤات validation وtest لمراجعة التقييم.
- `runs/fracatlas-yolo11n/results.csv`: سجل التدريب والتحقق.
- `train.py` و`network.py`: تجربة baseline أولية بـMobileNet وشبكة مربعات؛ فشل تقييمها في تحديد المواقع، لذلك لا تحملها خدمة التحليل. نتيجتها محفوظة في `artifacts/baseline/metrics.json` للتوثيق فقط.
- `dataset-source.json`: سجل Figshare ومعلومات المؤلفين والترخيص والملف المنزّل.

النموذج الخفيف اختير لإتاحة تدريب محلي على CPU؛ لا يساوي detector سريريًا معتمدًا. صور خارج النطاق قد تعطي اقتراحات مضللة، ولا يوجد مصنف موثوق لرفض الصور غير الطبية. تحفظ الإعدادات والأوزان ونواتج التدريب داخل `ml`؛ لا تستخدم خدمة Ultralytics السحابية.

## التقييم

تقسيم stratified تقريبي 70/15/15 على مستوى الصور، بعد استبعاد الصور غير القابلة للقراءة والتكرار المطابق SHA256 والتسميات المتناقضة. **لا تتوفر معرفات المرضى**، لذلك لا نضمن فصل المرضى أو استبعاد الصور المتقاربة بين المجموعات. هذا قيد على مصداقية التقييم، وليس تحققًا طبيًا مستقلًا.

تُختار checkpoint والعتبة باستخدام validation فقط؛ لا يُستخدم test للتدريب. يعرض المختبر precision/recall للصناديق عند IoU≥0.5، وحساسية/نوعية وجود اقتراح على مستوى الصورة. «حساسية الصور» لا تثبت صحة موقع المربع. التفاصيل والأعداد الفعلية ومصفوفة الأخطاء في `artifacts/yolo-metrics.json`؛ لا ننقل أرقام الورقة باعتبارها أداء نموذجنا.

لإعادة التدريب مع تعديل الخوارزمية أو التقسيم، احذف فقط ملفات `*-features.pt` الناتجة داخل `ml/artifacts` إذا تغير preprocessing أو المدخلات. لا تستخدم test لضبط النموذج، واستعمل بيانات خارجية مستقلة وتقييم مختصين قبل أي استخدام سريري.

## الخصوصية والنشر

الصور المرفوعة لا تُحفظ ولا تُرسل لخدمة خارجية؛ تعالج في الذاكرة على السيرفر المحلي. استخدم صورًا منزوعة بيانات التعريف الظاهرة، وليس فقط metadata. ملفات الأمثلة العامة مخزنة ضمن البيانات المنزلة. لا يوجد سجل مرضى أو قاعدة بيانات.

الحد: 12 MiB و25 مليون بكسل؛ JPEG/PNG/WebP فقط. DICOM غير مدعوم. الطلبات متسلسلة لتجنب استهلاك الذاكرة المتزامن. السيرفر مربوط بـloopback؛ هذه تهيئة تطوير محلية. استضافة Vite ثابتة وحدها لا تشغل Python؛ للنشر تحتاج خدمة Python منفصلة وreverse proxy، مع مصادقة وضبط الأحجام على مستوى خادم HTTP ومراجعة المتطلبات الطبية والخصوصية حسب استخدامك الفعلي.
